# Build brief — `reports` (compliance reporting from real data)

> Paste this whole file as the opening prompt. Fill the `[DECIDE]` block first.

**Size: ~1 week.** Build **after** consent, DSAR, grievance and retention are
live — a report over mock data is worse than no report.

---

## 1. The one rule that governs this module

**Every number in a report must be derived from a query, and every report must
state its own provenance.**

This codebase has already had to remove two fabricated artifacts: a dashboard
trend line invented from constants, and an "export signature" computed from
`rowCount * 7919`. Both looked like measurements. On a compliance product handed
to a regulator, a fabricated number is not a cosmetic bug — it is the thing that
destroys the product's reason to exist.

So: no placeholder figures, no rounded-for-looks values, no chart that renders a
shape when the underlying set is empty. **An empty report is a legitimate report**
and must render as one.

## 2. What exists

`/admin/reports` (`Reports.jsx`) with locked "Generate" buttons over mock rows.
`Capability.REPORT_GENERATE` and `AUDIT_READ` exist. The audit chain, consent,
DSAR and grievance data will be real by the time this is built.

`AuditHashBadge` and the hand-rolled SVG charts in `components/common/Charts.jsx`
already exist — no chart dependency, every series direct-labelled, colour never
the only signal. Keep that.

## 3. `[DECIDE]`

- `[DECIDE]` **Server-side PDF, or CSV/JSON only?** A PDF is what a DPO actually
  forwards to a board or a regulator. It also means a rendering dependency
  (WeasyPrint / Playwright) in the backend image.
  **Recommendation: CSV + JSON in v1, PDF immediately after**, with the PDF
  generated server-side. A client-generated PDF cannot be attested to.

- `[DECIDE]` **Are reports signed?** Today's audit export carries the chain head
  hash, which is honest and checkable. A true signature needs a key and key
  management.
  **Recommendation: keep the chain-hash approach for v1** and be explicit that it
  is not a signature. Do not ship anything labelled "digitally signed" until it is.

- `[DECIDE]` **Are generated reports stored or streamed?** Stored means a table
  of files containing personal data with its own retention problem.
  **Recommendation: stream by default**, store only if a customer asks, and give
  stored reports the same expiry treatment as DSAR access packages.

## 4. The report set

Each one answers a question a DPO or a regulator actually asks:

| Report | Question it answers |
| --- | --- |
| **Consent register** | who consented to what, under which notice version, when, how |
| **Consent activity** | grants / withdrawals / expiries over a period |
| **DSAR register** | every request, type, status, and whether it met the statutory deadline |
| **Grievance register** | every grievance, resolution time, escalations |
| **Retention & purge** | policies in force, purge runs, rows affected |
| **Audit extract** | filtered slice of the chain with `prev_hash`/`hash` and the head |
| **Breach register** | see `07-breach.md` |

## 5. Data model — probably none

Prefer **querying live** over materialising a `reports` table. A stored report is
a snapshot that can disagree with the data it came from, and when those two
disagree in a compliance product you have a liability rather than a document.

If the `[DECIDE]` says store, then:
```
report_runs      tenant_id, type, params jsonb, format, generated_by,
                 generated_at, row_count, chain_head_hash, expires_at
```
append-and-read, with an expiry, like DSAR packages.

## 6. Provenance block — mandatory on every report

Every generated report, in every format, carries a footer stating:

```
Generated at        <timestamptz, server clock>
Generated by        <user email>
Workspace           <tenant name and slug>
Period covered      <from> .. <to>
Rows in this report <n> of <total matching>
Audit chain head    <hash>   (verify: POST /v1/audit/verify)
Chain verified      OK | FAILED | NOT CHECKED
```

If the report is truncated or sampled, **say so in that block**. Silent
truncation reads as completeness.

## 7. API

```
GET  /v1/reports                       available report types + their params
POST /v1/reports/{type}/generate       body: period, filters, format
                                       -> streams CSV/JSON/PDF
GET  /v1/reports/{type}/preview        the same data, paginated, for the screen
```

Under `REPORT_GENERATE`. The **Auditor** role must reach reports and audit and
nothing else — the nav already reflects that; the routes must enforce it
independently.

## 8. Performance

Reports run over the largest tables in the system.

- Paginate the preview; stream the export. Do not build the whole result in
  memory and then serialise it.
- Every report's `WHERE` needs an index — check before shipping; a report that
  table-scans `audit_events` will be the first thing to take the API down.
- Cap the period. A five-year unfiltered audit extract is a denial of service
  someone will trigger by accident.

## 9. Frontend

- Reuse the existing SVG charts. No chart library.
- **Empty states are first-class.** "No consent activity in this period" is a
  real answer, and it must not render an empty axis that looks like a broken
  chart.
- Show the provenance block on screen too, not only in the export — the person
  reading the screen is making the same decisions as the person reading the file.
- Remove the fabricated `Math.abs(filtered.length * 7919)` signature pattern if
  any variant of it has crept back in.

## 10. Non-goals

- No BI/exploration tooling or custom query builder.
- No scheduled report emailing in v1 (notifications exist; this can come later).
- No cross-tenant benchmarking — an obvious idea and a data-sharing problem.

## 11. Tests

- every figure matches a direct query against the same data
- an empty period produces an empty report, not zeros dressed as measurements
- the provenance block is present in every format and names a truncation when
  one occurred
- the chain head hash in an audit extract matches `POST /v1/audit/verify`
- an Auditor can generate reports and gets 403 on consent write, DSAR process,
  users and retention
- period caps enforced
- cross-tenant: a report in tenant A never contains a tenant B row —
  assert on a seeded two-tenant fixture
- a large dataset streams rather than buffering (assert memory or chunking, not
  just success)

## 12. Definition of done

- [ ] Every report in §4 generates from real data
- [ ] Provenance block on screen and in every export
- [ ] `reports` flipped to `"live"` in `src/config/modules.js`
- [ ] If PDF is deferred, the UI offers CSV/JSON only — no dead PDF button
- [ ] Nothing in the module is labelled "signed" unless it is

## 13. House rules

Timezone-aware timestamps. Routers thin, services hold rules. No fabricated
numbers, anywhere, ever. Full list: [README.md](README.md).
